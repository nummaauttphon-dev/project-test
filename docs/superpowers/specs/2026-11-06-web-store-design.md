# Design: เว็บร้านค้าสำหรับทดสอบไอเดีย

- **วันที่:** 2026-11-06
- **สถานะ:** รอเจ้าของโปรเจกต์ตรวจ
- **Stack:** Next.js, React, TypeScript, Tailwind CSS, Supabase, Vercel

## 1. เป้าหมาย

สร้างเว็บขายสินค้าที่ต้องจัดส่ง เพื่อทดสอบว่ามีคนยอมจ่ายเงินจริงหรือไม่ โดยรับเงินผ่าน PromptPay และให้ลูกค้าแนบสลิป

**ตัวชี้วัดหลัก:** จำนวนออเดอร์ที่ชำระเงินแล้ว ดูได้จากหน้า `/admin` ส่วนเป้าตัวเลขและระยะเวลาทดสอบให้เจ้าของร้านกำหนดก่อนเปิดร้าน

**เกณฑ์ที่ถือว่าพร้อมทดสอบ:**

1. ลูกค้าสั่งซื้อและแนบสลิปจากมือถือได้จนจบ
2. แอดมินยืนยันการชำระเงินและกรอกเลขพัสดุได้
3. ลูกค้าเห็นสถานะล่าสุดจากลิงก์ออเดอร์
4. ระบบไม่ขายสินค้าเกินสต็อก แม้มีการสั่งซื้อพร้อมกัน
5. คนนอกเข้าถึงข้อมูลออเดอร์และสลิปของผู้อื่นไม่ได้

## 2. ขอบเขต

| หัวข้อ | รอบแรก |
|---|---|
| ตลาด | ขายเฉพาะในไทย ใช้เงินบาท หน้าเว็บภาษาไทย |
| สินค้า | ไม่เกินประมาณ 50 รายการ ไม่มีตัวเลือกย่อยและตัวกรองซับซ้อน |
| ลูกค้า | สั่งซื้อโดยไม่ต้องสมัครสมาชิก ติดตามผ่านลิงก์ของออเดอร์ |
| แอดมิน | ผู้ดูแล 1 คน ต้อง login |
| ค่าส่ง | อัตราเดียว แอดมินแก้ได้ |
| การจัดส่ง | แอดมินกรอกเลขพัสดุเอง |

**ไม่ทำในรอบแรก:** คูปอง, รีวิว, ระบบสมาชิก, Payment Gateway, การตรวจสลิปอัตโนมัติ, การเชื่อมระบบขนส่ง, การส่งอีเมลหรือข้อความแจ้งเตือน และการคืนเงินผ่านระบบ (ทำนอกระบบ)

## 3. Architecture

```text
ลูกค้า (ไม่ต้อง login) ──┐
                         ├──> Next.js บน Vercel ──> Supabase
แอดมิน (login) ──────────┘    Pages + Server Actions   ├─ PostgreSQL
                                                       ├─ Storage
                                                       └─ Auth (เฉพาะแอดมิน)
```

เลือกแนวทางให้ Next.js ทำงานฝั่ง server ทั้งหมด เพราะลูกค้าไม่ได้ login แต่ส่งข้อมูลส่วนบุคคลและสลิปเข้ามา การให้ทุกการแก้ไขผ่าน server จึงควบคุมได้ง่ายกว่าการเปิดให้ browser ต่อ Supabase โดยตรง

### องค์ประกอบ

| ส่วน | หน้าที่ |
|---|---|
| หน้าร้าน | แสดงสินค้า ตะกร้า หน้าสั่งซื้อ และหน้าติดตามออเดอร์ |
| หลังบ้าน `/admin` | จัดการสินค้าและสต็อก ตรวจสลิป กรอกเลขพัสดุ และแก้การตั้งค่าร้าน |
| Server Actions | ตรวจข้อมูลและสิทธิ์ เป็นทางเดียวที่ผู้ใช้แก้ไขข้อมูลได้ |
| PostgreSQL | เก็บข้อมูล และทำงานเกี่ยวกับออเดอร์กับสต็อกใน transaction |
| Storage | bucket `product-images` แบบสาธารณะ และ bucket `payment-slips` แบบส่วนตัว |
| Supabase Cron | เรียก `expire_orders` ทุก 5 นาที |
| Vercel Cron | เรียก `/api/cron/purge-slips` วันละครั้ง โดยต้องมี `CRON_SECRET` |

ตะกร้าเก็บใน `localStorage` เฉพาะรหัสสินค้าและจำนวน ราคาที่ใช้จริงมาจากฐานข้อมูลตอนสั่งซื้อเสมอ

การลบสลิปใช้ route handler แทนงานใน PostgreSQL เพราะการลบไฟล์ควรทำผ่าน Storage API เพื่อให้ไฟล์และข้อมูลอ้างอิงตรงกัน

### เส้นทางของออเดอร์

1. **สั่งซื้อ:** server ตรวจข้อมูล แล้วเรียก `create_order` เพื่อคำนวณยอด กันสต็อก และสร้างออเดอร์ จากนั้นส่งลูกค้าไป `/orders/[token]`
2. **ชำระเงิน:** หน้าออเดอร์แสดง PromptPay QR ตามยอด และเวลาที่เหลือ
3. **แนบสลิป:** server ตรวจไฟล์ เก็บใน bucket ส่วนตัว และเปลี่ยนสถานะเป็นรอตรวจ
4. **ตรวจสอบ:** แอดมินเปิดสลิปผ่าน signed URL อายุสั้น เทียบยอดกับแอปธนาคาร แล้วยืนยันหรือปฏิเสธ
5. **จัดส่ง:** แอดมินกรอกเลขพัสดุ และลูกค้าเห็นสถานะจากลิงก์เดิม

### สถานะของออเดอร์

| ค่าใน enum | ความหมาย | เปลี่ยนไปเป็น |
|---|---|---|
| `awaiting_payment` | รอชำระเงิน | `payment_review`, `expired`, `cancelled` |
| `payment_review` | รอตรวจสลิป | `paid`, `awaiting_payment`, `cancelled` |
| `paid` | ชำระแล้ว | `shipped`, `cancelled` |
| `shipped` | จัดส่งแล้ว | ไม่มี |
| `expired` | หมดอายุ คืนสต็อกแล้ว | ไม่มี |
| `cancelled` | ยกเลิก คืนสต็อกแล้ว | ไม่มี |

- สลิปไม่ผ่านจะกลับไป `awaiting_payment` และได้เวลาแนบสลิปรอบใหม่
- ช่วง `payment_review` ไม่มีการหมดอายุ เพื่อไม่ให้ออเดอร์ที่แนบสลิปแล้วถูกยกเลิกเอง
- การยกเลิกออเดอร์ที่ `paid` แล้ว แอดมินต้องคืนเงินนอกระบบเอง และหน้าจอต้องเตือนเรื่องนี้ก่อนยืนยัน

## 4. Database

เงินทุกจำนวนเก็บเป็นจำนวนเต็มหน่วยสตางค์ และ `order_number` เป็นเลขอ่านง่ายสำหรับคุยกับลูกค้า ซึ่งแยกจาก token ของลิงก์

### ตาราง

| ตาราง | คอลัมน์หลัก | หมายเหตุ |
|---|---|---|
| `products` | `id`, `slug` (unique), `name`, `description`, `price_satang`, `stock_quantity`, `image_path`, `is_active`, timestamps | สินค้าที่เลิกขายจะถูกซ่อน ไม่ลบทิ้ง |
| `orders` | `id`, `order_number` (unique), `status`, `customer_name`, `phone`, `shipping_address`, `subtotal_satang`, `shipping_fee_satang`, `total_satang`, `token_hash` (unique), `idempotency_key` (unique), `expires_at`, `tracking_number`, timestamps | ไม่มีตารางลูกค้าแยก |
| `order_items` | `id`, `order_id`, `product_id`, `product_name`, `unit_price_satang`, `quantity` | เก็บชื่อและราคา ณ ตอนซื้อ |
| `payment_slips` | `id`, `order_id`, `storage_path`, `review_status`, `reject_reason`, `reviewed_by`, `reviewed_at`, `file_deleted_at`, `created_at` | หนึ่งออเดอร์มีได้หลายสลิป |
| `store_settings` | `id`, `shipping_fee_satang`, `payment_window_minutes`, `contact_url`, `updated_at` | มีแถวเดียว |
| `admins` | `user_id` อ้างอิง `auth.users` | ปิดการสมัครสาธารณะของ Supabase Auth |
| `rate_limits` | `key_hash`, `action`, `window_start`, `count` | เก็บ hash ของ IP ไม่เก็บ IP ตรง ๆ |

### ความสัมพันธ์และการลบ

```text
products 1 ──< order_items >── 1 orders 1 ──< payment_slips
```

ทุก foreign key ของ `order_items` และ `payment_slips` ใช้ `ON DELETE RESTRICT` เพื่อรักษาประวัติออเดอร์

### กฎในฐานข้อมูล

- `stock_quantity >= 0`, `quantity > 0` และค่าเงินทุกคอลัมน์ `>= 0`
- `status` และ `review_status` เป็น enum
- `review_status` มีค่า `pending`, `approved`, `rejected`
- unique partial index ให้แต่ละออเดอร์มีสลิป `pending` ได้ครั้งละ 1 ใบ
- `reject_reason` ต้องมีค่าเมื่อ `review_status = 'rejected'`

### ฟังก์ชันใน PostgreSQL

| ฟังก์ชัน | หน้าที่ |
|---|---|
| `create_order` | ล็อกแถวสินค้าตามลำดับ `id` เพื่อกัน deadlock ตรวจสต็อกและราคาที่ลูกค้าเห็น คำนวณยอด สร้างออเดอร์ และตัดสต็อกใน transaction เดียว ถ้า `idempotency_key` ซ้ำจะคืนออเดอร์เดิม |
| `submit_payment_slip` | บันทึกสลิปและเปลี่ยนเป็น `payment_review` เฉพาะออเดอร์ที่ยังไม่หมดเวลา |
| `transition_order` | เปลี่ยนสถานะตามตารางด้านบน และคืนสต็อกเมื่อยกเลิก |
| `expire_orders` | เปลี่ยนออเดอร์ที่เกินเวลาเป็น `expired` และคืนสต็อก โดยเรียกซ้ำได้อย่างปลอดภัย |
| `check_rate_limit` | นับและตรวจจำนวนครั้งต่อ action แบบ atomic |

**การสร้าง token:** เมื่อลูกค้ากดสั่งซื้อซ้ำ ระบบต้องพาไปลิงก์เดิมได้ แต่ฐานข้อมูลเก็บเพียง hash ของ token จึงสร้าง token ฝั่ง server ด้วย HMAC จาก `idempotency_key` และ `ORDER_TOKEN_SECRET` โดย `idempotency_key` ต้องสุ่มใหม่ในแต่ละการสั่งซื้อ และยาวอย่างน้อย 128 บิต

**การหมดอายุ:** หน้าออเดอร์และ `submit_payment_slip` ต้องตรวจ `expires_at` เอง เพื่อให้ผลถูกต้องแม้ cron ยังไม่ถึงรอบ

### Row Level Security

เปิด RLS ทุกตาราง โดยค่าเริ่มต้นคือไม่อนุญาต

| ข้อมูล | การเข้าถึงจาก browser |
|---|---|
| `products` ที่ `is_active = true` | ทุกคนอ่านได้ |
| ตารางอื่นทั้งหมด | ไม่มีสิทธิ์โดยตรง |
| bucket `product-images` | ทุกคนอ่านได้ อัปโหลดผ่าน server เท่านั้น |
| bucket `payment-slips` | ไม่มีสิทธิ์โดยตรง แอดมินเปิดผ่าน signed URL |

ฟังก์ชันด้านบนต้องถอนสิทธิ์ `EXECUTE` จาก `PUBLIC`, `anon` และ `authenticated` เพื่อให้เรียกได้จาก server เท่านั้น

### Index

- `orders(status, created_at)`
- `orders(expires_at)` เฉพาะ `status = 'awaiting_payment'`
- `order_items(order_id)` และ `order_items(product_id)`
- `payment_slips(order_id)`
- คอลัมน์ `unique` ได้ index จาก constraint อยู่แล้ว

### Migration

ทุกการเปลี่ยน schema, RLS และฟังก์ชันเป็นไฟล์ migration ของ Supabase CLI ใน Git และทดสอบกับ Supabase ในเครื่องก่อนเสมอ

## 5. UI/UX

ออกแบบหน้าร้านโดยเริ่มจากจอมือถือ ส่วนโทนภาพลักษณ์และระบบดีไซน์จะกำหนดตอนเริ่มพัฒนาหน้าเว็บ ร่วมกับข้อมูลแบรนด์จากเจ้าของร้าน

### หน้าจอ

| Route | สิ่งที่มี |
|---|---|
| `/` | รายการสินค้า รูป ชื่อ ราคา และป้ายสินค้าหมด |
| `/products/[slug]` | รายละเอียด เลือกจำนวน และเพิ่มลงตะกร้า |
| `/cart` | แก้จำนวน ลบสินค้า และดูยอดรวมพร้อมค่าส่ง |
| `/checkout` | ชื่อ เบอร์โทร ที่อยู่ สรุปยอด และลิงก์ประกาศความเป็นส่วนตัว |
| `/orders/[token]` | สถานะ QR เวลาที่เหลือ การแนบสลิป เลขพัสดุ และช่องทางติดต่อร้าน |
| `/privacy` | ประกาศความเป็นส่วนตัว |
| `/admin/login` | เข้าสู่ระบบ ไม่มีหน้าสมัครสมาชิก |
| `/admin` | ออเดอร์รอตรวจ ออเดอร์ที่ชำระแล้ว ยอดขายรวม และสินค้าเหลือไม่เกิน 5 ชิ้น |
| `/admin/orders` | รายการออเดอร์พร้อมตัวกรอง โดยแสดงรายการรอตรวจก่อน |
| `/admin/orders/[id]` | ดูสลิปคู่กับยอดที่ต้องได้รับ ยืนยัน ปฏิเสธ กรอกเลขพัสดุ และยกเลิก |
| `/admin/products` | เพิ่ม แก้ไข ปรับสต็อก และซ่อนสินค้า |
| `/admin/settings` | ค่าส่ง เวลาแนบสลิป และช่องทางติดต่อร้าน |

ยอดขายรวมและจำนวนออเดอร์ที่ชำระแล้วนับเฉพาะสถานะ `paid` และ `shipped`

### พฤติกรรมเฉพาะ

- **จ่ายจากมือถือเครื่องเดียว:** มีปุ่มบันทึกรูป QR เพื่อเปิดจากแอปธนาคาร พร้อมแสดงยอดเงินเป็นตัวอักษร
- **กันลิงก์หาย:** ระบบไม่ส่งอีเมล จึงมีปุ่มคัดลอกลิงก์ คำเตือนให้บันทึกลิงก์ และช่องทางติดต่อร้าน
- **ราคาหรือสต็อกเปลี่ยน:** แจ้งรายการที่เปลี่ยนและให้ยืนยันใหม่ โดยไม่สร้างออเดอร์ด้วยยอดที่ลูกค้ายังไม่เห็น
- **สลิปไม่ผ่าน:** แสดงเหตุผลจากแอดมิน และแนบใหม่ได้จากหน้าเดิม

### สถานะของหน้าจอ

| สถานะ | การแสดงผล |
|---|---|
| Loading | โครงหน้าระหว่างโหลด และปิดปุ่มระหว่างส่งข้อมูล |
| Empty | ตะกร้าว่างหรือไม่มีสินค้า พร้อมข้อความและทางไปต่อ |
| Error | แสดงใต้ช่องที่ผิดโดยไม่ล้างข้อมูล และมีปุ่มลองใหม่เมื่ออัปโหลดล้มเหลว |
| Expired | แจ้งว่าออเดอร์หมดอายุ พร้อมปุ่มกลับไปสั่งซื้อ |

### Accessibility

เป้าหมายคือ WCAG 2.1 AA โดยใช้ semantic HTML, ใช้งานด้วยคีย์บอร์ดได้, มี focus ที่มองเห็นชัด, ทุกช่องมี label, screen reader อ่าน error ได้, ไม่สื่อสถานะด้วยสีอย่างเดียว, พื้นที่แตะมีขนาดเหมาะกับมือถือ และ QR มีข้อความกำกับ

## 6. Error Handling

Server Action ทุกตัวคืนผลลัพธ์รูปแบบเดียวกัน

```ts
type ActionResult<T> =
  | { ok: true; data: T }
  | { ok: false; code: string; message: string; fieldErrors?: Record<string, string> };
```

`message` เป็นภาษาไทยสำหรับผู้ใช้ ส่วนรายละเอียดทางเทคนิคอยู่ใน log ฝั่ง server โดยไม่บันทึก token, ที่อยู่ เบอร์โทร หรือเนื้อหาสลิป

| เหตุการณ์ | สิ่งที่ระบบทำ |
|---|---|
| ข้อมูลในฟอร์มไม่ถูกต้อง | แสดงใต้ช่องนั้นและคงข้อมูลไว้ |
| สต็อกไม่พอหรือราคาเปลี่ยน | ไม่สร้างออเดอร์ แจ้งรายการที่เปลี่ยน และให้ยืนยันใหม่ |
| กดสั่งซื้อซ้ำ | ใช้ `idempotency_key` เพื่อให้ได้ออเดอร์เดียว |
| ซื้อชิ้นสุดท้ายพร้อมกัน | คนแรกได้สินค้า อีกคนได้รับแจ้งว่าสต็อกไม่พอ |
| อัปโหลดสลิปล้มเหลว | สถานะไม่เปลี่ยน และลองใหม่ได้ |
| อัปโหลดสำเร็จแต่บันทึกข้อมูลไม่สำเร็จ | ลบไฟล์ที่เพิ่งอัปโหลด แล้วให้ลองใหม่ |
| แนบสลิปหลังหมดอายุ | ปฏิเสธ แล้วแนะนำให้ติดต่อร้านถ้าโอนเงินแล้ว |
| กดเปลี่ยนสถานะพร้อมกัน | `transition_order` ตรวจสถานะปัจจุบัน และยอมรับเพียงคำสั่งแรก |
| Token ไม่ถูกต้อง | แสดงหน้า 404 โดยไม่บอกว่าออเดอร์มีอยู่หรือไม่ |
| งาน cron ล้มเหลว | บันทึก log และรอบถัดไปทำต่อได้ เพราะเรียกซ้ำได้อย่างปลอดภัย |

## 7. Security

| ความเสี่ยง | วิธีป้องกัน |
|---|---|
| SQL Injection | ใช้ Supabase client และ parameter ของฟังก์ชัน ไม่ต่อ SQL จาก input |
| XSS | ใช้การ escape ของ React และไม่แสดง HTML จากผู้ใช้ |
| CSRF | ใช้การตรวจ Origin ของ Server Actions ร่วมกับ POST และ `SameSite` cookie |
| ไฟล์อันตราย | รับ JPEG, PNG, WebP ไม่เกิน 4 MB ตรวจเนื้อหาไฟล์จริง และตั้งชื่อไฟล์แบบสุ่ม |
| Spam จองสต็อก | จำกัดสั่งซื้อ 10 ครั้งต่อชั่วโมงต่อ IP, สินค้าไม่เกิน 10 ชิ้นต่อรายการ และแนบสลิป 10 ครั้งต่อชั่วโมงต่อออเดอร์ |
| ลิงก์ออเดอร์รั่ว | token เดาไม่ได้, เก็บเฉพาะ hash, ตั้ง `noindex` และ `Referrer-Policy: no-referrer`, ไม่เก็บ token ใน log และแสดงชื่อกับที่อยู่แบบย่อ |
| บัญชีแอดมินถูกยึด | ใช้ rate limit ของ Supabase Auth, เปิด MFA, ปิดการสมัครสาธารณะ และตรวจตัวตนกับสิทธิ์ซ้ำทุก Server Action |
| ข้อมูลลับรั่ว | `service_role` อยู่ในไฟล์ server-only, ไม่ commit `.env` และแยกค่าของแต่ละ environment |
| Cron ถูกเรียกจากภายนอก | ตรวจ `CRON_SECRET` ก่อนทำงาน |
| ช่องโหว่ของ dependency | ใช้ Next.js รุ่นล่าสุดที่มีแพตช์ความปลอดภัย และตรวจซ้ำก่อนเปิดร้าน |

ตามเอกสาร Next.js การตรวจ Origin จะปล่อย request ที่ไม่มี Origin ผ่านพร้อมคำเตือน จึงต้องตั้ง `SameSite` ของ cookie แอดมินด้วย และ Server Action ทุกตัวยังต้องตรวจสิทธิ์เอง

**ขนาดไฟล์สลิป:** Vercel Functions รับ request body ได้ไม่เกิน 4.5 MB ทุกแพ็กเกจ จึงจำกัดสลิปไว้ที่ 4 MB และตั้ง `serverActions.bodySizeLimit` ให้รองรับ ซึ่งเพียงพอสำหรับรูปสลิปและไม่ต้องเพิ่มการอัปโหลดตรงจาก browser ไป Storage

**PromptPay ID:** เก็บใน environment variable ฝั่ง server เพื่อให้คนที่เข้าถึงหน้าแอดมินแก้บัญชีรับเงินไม่ได้

**การตรวจสลิป:** แอดมินต้องเทียบยอดกับแอปธนาคารทุกครั้ง เพราะรูปสลิปอย่างเดียวปลอมได้

### ข้อมูลส่วนบุคคล

- ลบไฟล์สลิปอัตโนมัติ 90 วันหลังออเดอร์จัดส่ง ยกเลิก หรือหมดอายุ และเก็บแถว `payment_slips` ไว้พร้อม `file_deleted_at`
- เก็บข้อมูลออเดอร์ไว้เพื่อการจัดส่งและบัญชี รอบแรกยังไม่มีการลบข้อมูลลูกค้าอัตโนมัติ
- มีหน้า `/privacy` และเจ้าของร้านรับคำขอใช้สิทธิ์ข้อมูลผ่านช่องทางติดต่อร้าน

ตัวเลข 90 วันและเนื้อหาประกาศเป็นค่าเริ่มต้นทางเทคนิค ไม่ใช่คำแนะนำทางกฎหมาย เจ้าของร้านควรตรวจสอบกับข้อกำหนด PDPA ภาษี และบัญชีก่อนเปิดรับออเดอร์จริง

|---|---|

| `PROMPTPAY_ID` | Server เท่านั้น |
| `ORDER_TOKEN_SECRET` | Server เท่านั้น |
| `RATE_LIMIT_SALT` | Server เท่านั้น |
| `CRON_SECRET` | Server เท่านั้น |

### ขั้นตอนก่อนเปิดจริง

1. รัน test ทั้งหมดและ production build ให้ผ่าน
2. ทดสอบบน Vercel Preview กับโปรเจกต์ Supabase ที่แยกไว้
3. ขออนุญาตเจ้าของโปรเจกต์ก่อนรัน migration และ deploy ขึ้น production
4. ลองสั่งซื้อจริงบน production ตั้งแต่ต้นจนจบด้วยออเดอร์ทดสอบ แล้วตรวจ log และลบข้อมูลทดสอบเมื่อได้รับอนุญาต
